# D850 M-core（Firmware A / a1330）验证原型

> 状态：2026-11-18。实验性原型，不是整机 emulation，也不声称 M-core
> 已经“启动完成”。所有结论都来自本地提供的 a1330 镜像与 QEMU 运行记录。

## 1. 输入与镜像

- 镜像：`D850_6006432_MPU.bin`（1,048,576 字节，SHA-256
  `d23e6260…`），来自 WL-D850-FILES 仓库的 Tornado MPU dump；本次
  用 `d850_tornado_camera.pcap` 逐包重建，结果与仓库文件逐字节一致。
- 镜像身份：`D850   Firmware A Copyright Nikon Corp.`（0x1f08），
  版本块 `01 03 03`。
- 向量表在 0x0，**32 位大端**：MSP=`0x2000fa30`，reset=`0x0000c20d`。
- 指令流是**小端 Thumb**；即 BE8：指令取指小端，数据访问大端。
- 与 stock `a1330_010303.bin` 比较：1,048,576 字节中有 27,138 字节
  不同，集中在 `0x2000–0x8fff`（947 B）和 `0xf0000–0xfffff`
  （26,191 B）；其余逐字节相同。差异更像运行期写入/标定数据，
  未验证。

## 2. 机器模型

```sh
qemu-system-arm -M nikon-d850-mcore \
  -kernel /path/to/D850_6006432_MPU.bin
```

| 项目 | 取值 |
| --- | --- |
| CPU | `cortex-m4`（VFP 打开）；`-cpu` 可换 |
| Flash | 1 MiB @ `0x00000000`，直接装入 a1330 |
| SRAM | 256 KiB @ `0x20000000`（MSP 在 `0x2000fa30`） |
| 诊断 | 4 GiB catch-all；未建模访问记录 PC/地址/宽度/方向 |
| 默认入口 | 向量表：SP=`0x2000fa30`，PC=`0x0000c20d` |

### 2.1 QEMU 的 M-profile 向量表是 LE

QEMU 的 `arm_cpu_reset_hold` 和异常入口用 `ldl_p`（小端）读向量表；
a1330 的表是大端，直接读会得到 `0x30fa0020/0x0dc20000`。机器在把镜像
写入 flash 时，只把前 `0x40` 字节的 16 个表项做 32 位字交换（BE→LE），
给 CPU 用；原镜像和其余 1 MiB 不动。这是 **QEMU 取指夹具**，不是对
dump 的修改。

### 2.2 BE8 与 LE NVIC 的冲突

ARMv7-M 的 NVIC/SCB 在 QEMU 里是 `DEVICE_LITTLE_ENDIAN`。BE8 guest
写 `VTOR=0x2000fc00`、`CPACR=0x00f00000` 时，NVIC 收到的是
`0x00fc0020`、`0x0000f000`：

- VTOR 被截成 `0x00fc0000`，异常入口会去读错地址；
- CPACR 的 CP10/CP11 位被清掉，第一条 FPU 指令（`0x19b9e` 的
  `mrc p10,...`）触发 NOCP UsageFault。

机器在 `0xE000ED00` 加了一个 0x100 字节的 **大端 SCB 窗口**，
只接管 `VTOR`（0x08）和 `CPACR`（0x88），把值写进
`CPUARMState` 的 `v7m.vecbase`/`v7m.cpacr`，CPU 实际使用这两个字段。
这是 BE8 fixup，不是 SCB 模型。

### 2.3 第一批外设

reset 路径先碰两个块：

- `0x400F2000`：读、清 bit7、写回；`0x400F2004 = 0xB1`。
- `0x400F3000`：`0x400F3004` 是命令/状态握手——写
  `0xC35D0100 | (读回低 20 位)`，轮询高 12 位相等，再置位/轮询。
  目前用“读回最后写入值”的寄存器文件跑过握手。

## 3. 实测启动轨迹

```text
Loaded reset SP 0x2000fa30 PC 0xc20d
0xc2b0  rd 0x400f2000          ; clear bit 7
0xc2b6  wr 0x400f2000
0xc2be  wr 0x400f2004 = 0xb1
0x177c8 rd 0x400f3004          ; command/status handshake
0x177d2 wr 0x400f3004
0x177d4 rd 0x400f3004 (x N)
...
0x166aa rd 0x440ce000          ; pin/clock block (not a UART)
0x166b0 wr 0x440ce000 = 0x80000000
0x16724 rd 0x440ce004
0x16732 wr 0x440ce004 = 0x40000000
0x16754 rd 0x440ce008
0x1675c wr 0x440ce008 = 0
0x1673c rd 0x440ce004
0x1674a wr 0x440ce004 = 0x03000000
```

之后不再有未建模访问；QMP 在 3 s 时读到：

```text
R15=0000c05e  R14=0000c05f  R01=e000ef00  R13=2000fa28
XPSR=61000000  T priv-thread
```

即停在 `0xc05e`（`0xc044` 函数的 `bx lr`），函数刚向
`0xE000EF00`（NVIC STIR）写过值。没有异常、没有 lockup；这是一个
稳定的 idle/loop 状态，不是崩溃。

## 4. 现在的边界

- `0x440CE000` 是 **pin/clock/GPIO 块，不是 UART**（见 §4.1）；启动路径
  只写了 8 次控制寄存器，没有写任何串口数据寄存器。
- `0x440CE004/008/010` 是它的全局配置；`0x24 + 0x10*n`（n=0..7）是
  8 个通道/引脚的配置寄存器；`0x166b4/0x166f0` 按索引读写这些通道。
- 真正的串口候选是 `0x440C4000..0x440C4900`（8 个实例，0x100 步进；
  0x1f218 有一张基址表；0x129bc 用 `0x440C4600` 做初始化/计数器读取）。
  启动路径没有访问这个范围。
- STIR 写入的 IRQ 号（观测到 `0x8f`）超出当前 `num-irq=96`；中断
  行为未建模。
- 异常路径仍会从 `VTOR=0x2000fc00` 读 SRAM 向量表；该表是 BE，
  QEMU 会按 LE 读。当前没有异常，所以还没触发这个问题。
- `0x400F2000`/`0x400F3000` 是寄存器文件，不是硬件模型。

### 4.1 为什么没有 TX 字节

按“给 0x440CE000 建 UART 模型”的假设做了反汇编核对，结论是假设不成立：

- `0x166aa`：读 `[0x440CE000]`，置 bit7；`0x16724/0x1673c`：改
  `[0x440CE004]` 的 bit0/1/3/6；`0x16754`：改 `[0x440CE008]` 低 7 位；
  `0x16760/0x16774`：改 `[0x440CE010]` 的 bit6/7。这是典型的
  引脚/时钟使能序列，不是 TX。
- `0x166b4/0x166f0` 用 `tbb` 选择 `0x24/0x34/.../0x94` 八个通道，
  读写的是 16 位配置值；`0x166ec` 读 `[0x440CE010]` 状态。
- UART 配置函数在 `0x16576/0x16598/0x165a8/0x165c0`，参数是
  `0x440C4xxx` 基址；`0x16570` 读 `[base+0x1c]` 的 16 位计数器
  （更像波特率/时钟计数）。`0x129bc`（`0x440C4600` 初始化）没有
  直接调用者，可能在函数表里。
- 启动路径是 `0xC20D → 0xC2AE → 0x177C4 → 0x83A0/0x1CE34/0x2B4`；
  trace 里没有任何 `0x440C4xxx` 访问。

所以在这条启动路径上**没有 TX 字节可抓**；给 0x440CE000 做 UART
模型只会看到控制写。要继续拿输出，得先找到/触发 console 路径。

## 5. 下一步

1. 找 console 初始化/打印路径：`0x129bc`/`0x12a3c` 的调用者（可能在
   函数表/RTOS 任务里），或 `0x16576` 的 21 个调用者中是否有 putc。
2. 如果 console 确实在 RTOS 任务里，先把 STIR/IRQ 和定时器模型补上，
   让 idle 循环能继续跑。
3. 给 `VTOR=0x2000fc00` 的 SRAM 向量表做 BE/LE 处理，验证异常路径。
4. 若 M-core 的输出能确认“启动完成”，再考虑与 A-core 的交接
   （谁释放 A-core、谁提供 `0x400E8450` 的参数）。

> QEMU 控制流，不代表真机寄存器语义。
